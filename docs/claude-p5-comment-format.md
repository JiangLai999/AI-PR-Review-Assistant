# P5 前端：GitHub 评论 v2 格式与可渲染性只读审计（任务 `claude-p5-comment-format`）

**一句话结论**：v2 评论的 GFM 结构本身是干净的（`<details>/<summary>/<b>/<sub>` 全部配平、
Markdown 与 HTML 的空行边界正确、路径与 `<>&#` 的转义到位），未发现会破坏整条评论的渲染缺陷；
问题集中在「评论对读者作出的承诺」上——**fork PR 行链接的降级逻辑文档声称有、代码里没有**（blocker）、
`run` 句柄不可用、审查时间与审查覆盖度缺失、评论体积无上限（major）。

- 审计类型：只读（未运行测试、未改任何文件、未访问网络、未执行 git 操作）
- 审计对象：`_p5_verify/reports/p5-v2-comment-preview.md` + `src/ai_pr_review/services/report_renderer.py`
  的 `render_github_comment` / `_github_*`
- 结论文件：本文件（`docs/claude-p5-comment-format.md`，write_scope 内唯一写入）

## 3. a) GitHub Flavored Markdown 可渲染性

## 4. b) 信息层级

**首屏（前 13 行）能拿到什么**：目标仓库 + PR 号 + 变更文件数（L3）、严重级别分布（L5）、
证据健康（L6）、模型/run/耗时/成本（L7）、Top 3 优先修复（L9-13）。这部分设计达成度高，
排序规则为「严重级优先、同级按置信度降序」（`:404-408`），产物 Top 3 = 2 critical(91%) + 1 high(94%)，
可复现且诚实（标题写的是「优先修复」，不是「风险最高」）。

**缺口**：

- **F6（major）目标 PR 不可点击，也没有作者**。`RenderedReportContext.pr_url` 在 `:153` 定义、
  `:842` 赋值，但 v2 从未使用（`_render_github_comment_v2` 全文未出现 `context.pr_url`）；
  `:420-423` 的 `target` 行只输出 `` **`repo`** · PR #N `` + 可选标题。产物 L3 因历史 Run 无标题
  （`publish_service.py:46`）退化为「仓库 · PR #31 · 18 个变更文件」——读者从通知点进来后，
  无法一键回到 PR 本体。`author` 同样存在于 context（`render_markdown` 在 `:329` 用了），v2 不用。
- **F4（major）不显示审查覆盖度**。见 §6。
- **F8（minor）严重级图标在同一评论内不自洽**：折叠标题与 Top 3 用 `GITHUB_SEVERITY_ICONS`
  （critical=🛑，`:517`/`:604`），卡片标题却用 `MARKDOWN_HEADING_ICONS`（critical=❌，`:653`）。
  产物 L11（🛑）与 L18（❌）指向同一条问题；high 两级恰好都是 ⚠️ 所以看不出来。
- **F15（minor，可选）Top 3 与下方详情的重复无锚点**：Top 3 的第 3 条落在 high 块（默认折叠，
  `:609`），想看详情必须再点一次；且 Top 3 行内没有锚点可跳。`:607-608` 的注释说明这是有意的取舍
  （「everything else stays one click away」），故仅作可选优化。
- **F11（minor）「18 个变更文件」与「📄 逐文件摘要（14 个文件）」两个计数并存且语义不同**（L3 vs L138）：
  前者是 PR 变更文件数（`run.total_files`），后者是模型摘要里可识别的 `path:` 段落数
  （`_github_summary_block`，`:750-755`）。同一单位「文件」在一屏内出现两个值而不加限定，读者会问「另外 4 个呢」。

## 5. c) 本地化一致性

**界面语言与内容语言是两条线**（`report_renderer.py:59-60` 注释 + `prompt_assembler.py:135-146`
的 `LANGUAGE:` 指令），产物正是这样：chrome 全中文，内容中英混排。**内容的中英混排不属于本审计的
改进项**（模型/规则输出，不得改写内容本身）；下面只谈 chrome。

- chrome 基本全中文：标题、目标行、统计行、证据徽章、问题/建议、结论摘要、逐文件摘要、
  优先修复、页脚前缀均为中文（产物 L1-L13、L16、L21-23、L35、L107、L138、L199）。
- **F13（minor）`**Code**：` 未本地化**：`:683` 与 `:690` 在 zh 分支下仍输出英文 `Code`，
  且与相邻中文标签共用全角冒号，形成「**Code**：」；同处上下文的 `problem_label`/`suggestion_label`
  （`:663-664`）已本地化，属明显遗漏。默认不显示（片段开关关闭），开启后才会出现在每张卡片上。
- **F10（minor）`run` 未本地化**：`:535`/`:786` 输出 `run \`8c2fc8ec\``，同一行的 `模型`/`提交` 已本地化
  （产物 L7、L199）。若「run」是刻意的稳定标识符可保留，但需与「模型」「提交」的口径一致（建议 zh 用「运行」）。
- **F10（minor）`sources` 是唯一既不规范化也不本地化的 Finding 字段**：产物 L19/L26 显示
  `` `安全` ``（category，已本地化）紧跟 `` `static_rule` ``（source，原样英文）。注意
  **source 的值可能是模型自己填的**：`Finding.sources` 是无约束的 `list[str]`
  （`prompt_assembler.py:75`），而 JSON Schema 是直接交给模型的（`:249-251`、`:151-152`），
  产物里出现的 `diff` / `changed_line_review` / `security` 就不在流水线的任何枚举里
  （静态分析器只写 `static_rule`：`static_analyzer.py:192`、`python_ast_analyzer.py:521`）。
  因此**不应对它做显示层翻译**（会违反「内容不改写」原则），正确做法是在 schema/validator 层
  像 `category` 那样收敛：`category` 已有 `pattern` + `normalize_category`（`prompt_assembler.py:60-65`、`:80-100`）
  与 `GITHUB_CATEGORY_LABELS_ZH`（`:75-83`、`:642-648`），而 `sources` 没有——这个不对称还影响控制流：
  `finding_validator.py:61` 与 `finding_localizer.py:79` 都用 `"static_rule" in finding.sources` 判分支，
  模型写个变体就会被当成 `ai_analysis` 或跳过中文映射。
- **F7（minor，见 §6）三套证据状态术语并存**：评论用「证据有效/待复核/证据不成立/未验证」（`:486-489`），
  终端明细用「证据有效/待人工确认/证据不成立/未校验」（`:262-266`），终端汇总行用「有效/待确认/无效/未校验」（`:227-228`）。

## 6. d) 准确性与诚实性

### F1（blocker）fork PR 的行链接降级：文档声称有，代码里没有

`_github_blob_link` 的 docstring（`:543-548`）写着「Fork PRs keep the head commit outside the base
repository, so a missing sha falls back to plain text rather than a link that 404s」，但实现（`:549-560`）
**只判断 `head_sha` 是否为空**，没有任何 fork 判定；`PRData`（`models/pr_data.py:49-92`）也只有
`owner`/`repo`/`head_sha`，没有 head 仓库或 `is_fork` 字段，渲染器在结构上**无法**知道自己正在为一
个 fork PR 生成 base 仓库的 blob 链接。而 fork PR 的 `head_sha` 恰恰**非空**
（`review_orchestrator.py:314` 存 `pr_data.head_sha`，`publish_service.py:248` 原样取出），
也就是说「为 fork 准备的那条回退」对 fork 场景永不触发。
后果：按任务前提，fork PR 下产物 L11-13、L19、L26 这类
`https://github.com/{base}/{base}/blob/{fork-head-sha}/path#L237` 全部 404，
而评论里没有任何提示，读者只会认为「行链接坏了」。
（诚实标注：本审计无法联网，未能实测 GitHub 对 fork head sha 的解析行为；这里判定的是
**代码与其自身文档的承诺不一致**，以及缺少任何降级/提示路径。）

### F2（major）未标注审查时间与陈旧度

`GitHubCommentMeta`（`:132-146`）没有时间字段，`:530-540` 与 `:769-789` 因此不可能输出时间；
而发布路径手上就有：`get_run_summary` 的 SELECT 已含 `created_at`（`result_store.py:220`，
`created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP`，`:324`），`publish_service.load_target` 也拿到了整个
`run` 字典（`:221`、`:238`），只是没往下传。产物 L7/L199 因此只有 `run 8c2fc8ec · 66.1s · $0.5710 · 提交 226e769`。
对一个**以「评论形式发布到 PR」**的产物来说，GitHub 只会显示「评论发布时间」，读者没有任何办法
区分「刚跑的」和「一个月前跑的重新发布」。这与项目自己在 `publish_service.py:42-48` 表达的
原则（宁可用显式占位也不用假信息）方向一致，但时间这一项漏了。

### F3（major）发表路径丢掉了审查覆盖度

产物 L3「18 个变更文件」+ L5「10 个问题」的组合会被读成「这 18 个文件都审过了」。
但 `total_files` 只是 PR 变更文件数；真正被审的文件数是 `included_files`（`review_orchestrator.py:316`），
被过滤掉的是 `excluded_files`（`:317`）。这两列 `get_run_summary` 已经查出来了
（`result_store.py:220`），却被 `_stored_run_pr_data`（`publish_service.py:141-177`）丢弃——
它只读了 `total_files`（`:154-157`）并塞进 `_StoredRunPRData._files_changed`（`:68-81`）。
同一信息在别处都有：本地 markdown 报告有过滤摘要（`cli.py:1554+`），后端报告有
`files_reviewed`/`files_skipped`（`jsonl_server.py:1112-1113`），唯独发到 GitHub 的正文没有。

### F4（major）评论体积无上限，「折叠」只藏不删

`_GITHUB_FOLD_THRESHOLD = 320`（`:129`）只决定 `<details>` 是否包住问题/建议文本，
**字符数一个都不会少**；`_render_github_comment_v2`（`:395-473`）没有任何总长度预算或截断，
`publish_service._post_comment`（`:294-307`）也没有（失败只会得到一句 `publish_failed`）。
实测本产物 12,377 字符 / 10 条问题 ≈ 666 字符/条（严重级块 6,656 字符 / 10 条），另有逐文件摘要
4,764 字符。据此**外推**（非实测）：约 90 条问题的评论就会逼近 GitHub 单条评论 65,536 字符的正文上限，
届时发布会硬失败——而那正是最需要评论的大 PR。
仓库里已有截断工具（`jsonl_server.py:820-845`、`prompt_assembler.py:309-312`），评论正文这条路径没有用上。

### F5（major）证据徽章把「校验器没发现问题」表述成「证据有效」

`finding_validator.py:17-53` 定义 `valid` 的条件是：文件与所审文件一致、行号在文件内、
行范围落在 diff 的变更行上、代码片段能在文件内容中找到（`:19-40`），任一不满足则降级（`:42-53`）。
产物 L11-12 因此出现「🛑 严重 · 91% · ✅ 证据有效」——**证据有效**在这里只意味着
「引用位置与片段自洽」，不意味着这条 hard-coded secret 是真的凭证（该条来源是 `static_rule`）。
`_github_evidence_badge`（`:483-493`）与统计行的「**证据健康**」（`:522-527`）、页脚的
「9/10 条证据通过校验」（`:778`）都用了结论式措辞，且正文没有任何图例说明校验范围。

### F9（minor）统计块换行约定不一致（可靠性取决于渲染器）

实测：L5 行尾两个空格（硬换行）＝ `True`，L6/L7 ＝ `False`。代码上 `:527` 显式写死了 `"  \n"`，
`_github_meta_line` 的返回值却没有。若下游渲染器把软换行折叠成空格（很多 Markdown 实现如此），
L6/L7 会连成一行：「… ❔ 未验证 0 模型 `deepseek-flash` · run `8c2fc8ec` · 66.1s · $0.5710」。
（GitHub 的 issue/PR 评论对段内软换行的具体策略本审计无法离线核实，见 §8；无论哪种策略，
**同一块内一半硬换行一半不换行**都是隐患，何况「去掉行尾空白」是常见编辑器/格式化动作——
本仓库的提交历史里就有「trailing whitespace removed」这类改动。）

### F11（minor）成本/耗时字段可能误导

`:536-539` 输出 `66.1s` 与 `$0.5710`：成本来自本地估算而非账单
（`review_orchestrator.py:306` → `ai_client.py:179-181` → `cost_controller` 的 token×价目累计），
4 位小数给出虚假精度且没有任何「估算」标注；`cost=0.0` 时会输出 `$0.0000`，读起来像「免费」

### F2'（minor）历史 Run 的占位不会被误读，但降级是静默的

`UNKNOWN_PR_TITLE = ""` + `if context.pr_title`（`:421-422`）→ 无标题时整段消失，不会出现

唯一代价是读者无法区分「这个 PR 没有标题」和「这条 Run 太老没存标题」——配合 F2/F6 一起修更自然。
