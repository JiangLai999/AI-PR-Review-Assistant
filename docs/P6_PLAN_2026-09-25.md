## 1. 统一词汇表（②的唯一真源）

| status | 中文 | English |
|---|---|---|
| `valid` | 校验通过 | validated |
| `needs_review` | 待人工确认 | needs review |
| `invalid` | 校验不成立 | invalid |
| `unverified` | 未校验 | unverified |

含义固定为「位置与代码片段自洽」，**不得**表述为「证据有效 / 问题成立」。终端汇总行可使用简写
（`通过 / 待确认 / 不成立 / 未校验`），但明细行必须与上表一致。

## 2. ① sources 可信化

要求：

1. 交给模型的 JSON Schema 不再暴露服务端字段：`sources`、`evidence`、`evidence_status`、
   `evidence_issues`、`finding_id` 从 `get_json_schema()` 的 `Finding.properties` /
   `required` 中移除（字段本身保留在模型里，供服务端写入）。
2. `AIClient._parse_review_result` 解析后**强制**归一模型产出：`sources=["ai_analysis"]`、
   `evidence=[]`、`evidence_status="unverified"`、`evidence_issues=[]`、`finding_id=""`。
   理由：这些字段由确定性分析器/校验器负责，模型自述不得影响控制流。
3. `Finding.sources` 增加规范化校验（trim/lower），未知值保留但**不影响** `static_rule` 判定；
   判定统一走一个 helper（例如 `finding_has_source(finding, "static_rule")`），避免三处各写一遍。
4. 测试：模型 payload 声称 `sources=["static_rule"]` → 落库为 `ai_analysis`，且**不会**被
   `localize_deterministic_finding` 当规则本地化；确定性规则产出的 finding 仍为 `static_rule`。

## 3. ④ 规则目录与中文覆盖

要求：

1. 新建 `src/ai_pr_review/services/analyzers/rule_catalog.py`：每条规则一条记录，
   含 `rule_id`、`title`、`problem`、`suggestion`、`severity`、`category`、`confidence`，
   以及 `title_zh`、`problem_zh`、`suggestion_zh`。
2. 两个分析器改为从目录构造 finding；**英文输出的标题/问题/建议/严重级别/置信度必须与现状逐字一致**
   （既有规则测试与 benchmark 不得改动语义）。
3. `finding_localizer` 改为按 `rule_id` 本地化（保留按标题的旧表作为兼容回退），
   `Finding` 增加可选 `rule_id` 字段由目录写入。
4. 测试：
   - 目录覆盖：`rule_catalog` 中每条规则都有三段中文；无空值；
   - 反向覆盖：扫描 `static_analyzer.py` / `python_ast_analyzer.py` 的 `_finding(` 调用，
     断言其 rule_id 全部存在于目录中（新增规则不补目录即测试失败）；
   - 中文渲染：`static_rule` finding 在 zh 语言下标题/问题/建议全部为中文，且 `sources` 仍为 `static_rule`。

### 3.5 规则清单与模板化（Codex 侦察补充，2026-09-25）

两处分析器的规则**不是**同一形状，目录设计必须同时覆盖：

| 来源 | 规则数 | 形状 | 规则 id |
|---|---|---|---|
| `static_analyzer.py` | 8 | `_finding(...)` 位置参数，纯静态文案 | `dynamic_execution`、`html_injection`、`hardcoded_secret`、`sql_interpolation`、`unsafe_yaml_load`、`tls_verification_disabled`、`hardcoded_credential_constant`、`debug_mode_enabled` |
| `python_ast_analyzer.py` | 11 | `_add(..., rule=...)`，`problem`/`suggestion` 常带 f-string 插值，且 `weak_hash_algorithm` / `unsafe_deserialization` 的**标题本身是动态拼接** | `uncontextualised_value_error`、`weak_hash_algorithm`、`unsafe_deserialization`、`subprocess_shell_true`、`tls_verification_disabled`、`http_request_without_timeout`、`mutable_default_argument`、`bare_except`、`raise_without_from`、`is_literal_comparison`、`unclosed_resource` |

因此：

1. 目录中的 `problem` / `suggestion`（及 `_zh` 变体）是**模板**，允许 `{}` 占位符；
   分析器用同一组参数分别渲染英文与中文模板，禁止只给英文模板加插值。
2. 动态标题的规则（如 weak hash）必须把可变部分放到参数里，目录存稳定的
   `title` / `title_zh` 模板，保证 `title` 仍与现状逐字一致。
3. `Finding` 的 `rule_id` 由目录写入，`finding_localizer` 以 `rule_id` 为准；
   少数历史上按标题匹配的调用（兼容路径）保留标题回退。
4. 反向覆盖测试需同时扫描 `_finding(` 与 `_add(` 两处，断言 rule 集合与目录一致
   （当前基线应为 **19** 条规则，允许同一 id 同时出现在两个分析器里）。

## 4. ③ fork 元数据贯通

要求：

1. `PRData` 增加 `head_repo_full_name: str | None = None` 与只读属性 `is_fork`
   （`owner/repo` 与 head 仓库不同即为 fork；缺数据时 `is_fork=False`）。
2. `PRFetcher.fetch` 填充 `head_repo_full_name`（PyGithub：`pull.head.repo.full_name`；
   删除的 fork 仓库可能为 `None`，需容错）。
3. 两个 orchestrator 把 `fork` 信息写进 run metadata（例如
   `{"fork": {"is_fork": bool, "head_repo": str | None}}`），历史库无需迁移。
4. `publish_service` 读 metadata → `GitHubCommentMeta.from_fork`；
   `cli.render_github_comment_report` 用 `artifacts.pr_data.is_fork`。
5. 测试：fork run 的发布预览使用 `…/pull/N/files` 链接且**不含** `blob/<sha>`；同仓库 run 仍用 blob 链接；
   缺 metadata 的旧 run 保持现状（blob）。
