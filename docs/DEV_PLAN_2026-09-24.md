## P2 安装版统一（比赛硬需求）

问题：wheel 仅打包 `src/ai_pr_review`，`_open_tui_frontend` 依赖源码树 `parents[2]/frontend/tui`，安装版必然回退旧 Chat。

两条路线，先验证 A，失败退 B：

- 路线 A：`bun build --compile` 产出单文件 `pr-review-tui.exe`，随 wheel 分发，运行时不依赖 node_modules。需先验证 OpenTUI 原生依赖能否干净编译。
- 路线 B：把 `frontend/tui`（源码 + 依赖）作为包数据分发，`_open_tui_frontend` 改用包内资源路径（对齐 `web_static` 的做法）。

出口条件：干净虚拟环境 `pipx install` 后 `pr-review chat` 打开与源码版同一套 OpenTUI；无 Bun 时给出可操作错误而非静默降级；wheel 体积报告。

## P3 后端健壮性

按风险排序：

1. `/model local` 覆盖远程 provider 与已存密钥且不可回切（Claude F3，数据丢失）→ 双槽位或保留远程配置。
2. `ModelSelector` 硬编码 Ollama、无健康探测，`local_provider` 是死配置（F4）。
3. 审查取消尾窗：`run_review` 返回后仍会写库并报完成；同 session 有 chat 时 review 无取消入口（F17）。
4. `review.*` 事件未按 session 过滤；chat 仅靠 `assistant.finished` 落消息（F9/F10）。
5. 流式 `emit().result()` 无超时、跨线程 close 竞态；Anthropic 走完整回退（F11）。
6. 非法 `AI_PR_REVIEW_PROVIDER` 直接崩后端（F13）。
7. `agent_bridge` 加固：原子写、锁 TTL、`report` 状态机、`task_id` 净化（F5/F6/F12）——协作总线已在使用，崩溃死锁会直接影响调度。
8. Web `serve` 的 `config_path` 注入（F19，2 行修复，顺手）。
