# 思考档位（reasoning_effort）实测报告

日期：2026-09-26 · 脚本：`_p5_verify/p6proto/probe_reasoning_effort.py`
模型：`deepseek-flash`（DeepSeek 官方 API）· 同一道需要推理的题，每档跑 2 次

## 为什么要先实测

用户明确要求"**思考档位要有实际作用**"——如果参数只是被 API 收下、行为不变，
那这个档位就是骗人的摆设。所以先测，再决定要不要做。

## 原始数据

| 档位 | reasoning 字符 | completion tokens | 总 tokens | 耗时(s) |
|---|---|---|---|---|
| `minimal` #1 / #2 | 325 / 487 | 293 / 400 | 367 / 474 | 2.0 / 2.7 |
| `low` #1 / #2 | 510 / 361 | 416 / 301 | 490 / 375 | 2.5 / 2.1 |
| `high` #1 / #2 | 711 / **1715** | 255 / 499 | 329 / 573 | 1.7 / 3.2 |
| `max` #1 / #2 | 334 / 780 | 279 / 384 | 353 / 458 | 2.2 / 2.4 |
| **未传该参数** #1 / #2 | **1358** / 1048 | **864** / 416 | **938** / 490 | 5.0 / 2.8 |

## 结论

**DeepSeek 的 `deepseek-flash` 对 `reasoning_effort` 无实际响应。**

依据三条：

1. **档位内部波动 > 档位之间差异**：`high` 两次分别是 711 与 1715 字符；`minimal`（325）甚至超过 `high` 的第一次（711）。没有单调关系。
2. **不传参数时反而最高**（1358 / 1048 字符，864 completion tokens）：如果参数有效，最高档应显著高于默认。
3. **API 不报错**（HTTP 200）——参数被"收下"但被忽略，这是最容易被误当成"支持"的情形。

## 对方案的影响（重要）

**原方案 C6（五档可选）作废**。新原则：**档位只在"实测有效"的供应商上开放**。

| 供应商 | 参数 | 证据 | 档位是否开放 |
|---|---|---|---|
| DeepSeek（flash / reasoner） | `reasoning_effort` | **本报告：无实际效果** | ❌ **不开放**，UI 禁用并说明 |
| MiMo Code | `variant: minimal\|high\|max` | 官方 CLI 帮助文本（`--variant`） | ✅ 开放（**实现时需同样实测确认**） |
| OpenAI 推理系 | `reasoning_effort` | 官方文档 | ✅ 开放（同上，实测确认） |
| 其它 / 未知 | — | 无 | ❌ 不开放 |

### 实现要求（写入 C6）

1. **能力表**：每个 provider 显式声明"是否真正支持档位 + 参数名"，**默认不支持**。
2. **不支持的模型**：
   - `/think` 明确回一句「当前模型 `<name>` 不支持调整思考强度」，**不假装写入了配置**；
   - 配置助手里该项**置灰**并给出同样说明。
3. **支持的模型**：实现时必须**先跑一次同款实测**（不同档位要有可观察的单调差异）才算"支持"，
   实测脚本已就位，可直接扩展为验收用例。
4. **绝不把"API 不报错"当成支持**——DeepSeek 就是反例。
