# AI PR Review Assistant 参赛版改造升级执行计划

> 制定日期：2026-09-20  
> 当前版本：P0 验收完成，进入第二阶段  
> 当前原则：先稳定、再体验；先闭环、再包装；不在未验收前进行 commit / push。

## 一、总目标

将 AI PR Review Assistant 从“功能完整的 AI PR 审查工具”升级为：

> **可现场演示、可解释、可复盘、可信赖的本地 AI 代码审查工作台。**

参赛版必须同时满足：

1. CLI 和 Web 两种入口能力一致；
2. 离线 Demo 不依赖外部网络也能完成完整演示；
3. 真实 GitHub + DeepSeek 链路可运行；
4. 每条 Finding 都有证据和可追溯来源；
5. 评委在 30 秒内理解项目价值，在 3 分钟内看到完整闭环；
6. 代码、测试、安装、文档和演示材料可以冻结交付。

# 四、详细执行计划

## 阶段 P1：Web 工作台产品体验改造

### P1.1 审查工作台首屏重构

目标：用户打开页面后，能立即完成“输入 PR → 选择模式 → 开始审查”。

任务：

- [ ] 将 PR URL 输入提升为首屏主操作；
- [ ] 明确区分“生成计划”和“完整审查”；
- [ ] 显示预计步骤、预计耗时和是否调用模型；
- [ ] 让审查启动后的进度区域自动进入视口；
- [ ] 将取消任务按钮放到进度区域的可见位置；
- [ ] 统一按钮的 loading、disabled、success、error 状态；
- [ ] 对无效 PR URL 提供即时修复提示；
- [x] 增加“使用离线 Demo”快捷入口。

验收标准：

- 首屏不滚动即可开始一次审查；
- 用户能清楚知道当前是“计划模式”还是“完整审查模式”；
- 开始后 1 秒内能看到阶段进度；
- 错误信息可读且不会出现裸 `Failed to fetch`。

## P1.2 结果可信度视觉化

目标：让评委一眼看懂系统为什么可信。

任务：

- [ ] 强化风险总览卡片：严重度、Finding 数量、证据状态；
- [ ] 为 `valid / needs_review / invalid` 设计统一状态徽章；
- [ ] 展示 Finding 来源：规则、AST、AI、跨文件；
- [ ] 增加“证据链完整度”摘要；
- [ ] 让文件、行号、Diff 关联成为 Finding 卡片的主信息；
- [ ] 将跨文件接口影响单独做成影响卡片；
- [ ] 对高风险 Finding 提供更明确的视觉优先级；
- [ ] 保留原始 JSON，但降低其首屏干扰。

验收标准：

- 评委不打开原始 JSON 也能理解 Finding 证据；
- 高风险问题和待人工复核问题明显区分；
- Finding 卡片在桌面端和 Edge 浏览器显示正常。

## P1.3 状态和异常体验

- [ ] 统一空数据状态：没有历史、没有 Finding、没有凭据；

# 五、每轮执行规则

每一轮必须遵循：

1. 先检查当前工作区和已有改动；
2. 只实现本轮明确范围；
3. 不覆盖用户已有改动；
4. 修改后立即运行针对性测试；
5. 通过后再运行构建或全量测试；
6. 汇报改动、验证结果和遗留问题；
7. 未经用户确认不 commit、不 push。
